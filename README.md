# Бот: бюджетные билеты (Вьетнам ↔ Россия)

Telegram-бот, который раз в N минут проверяет цены на билеты между
аэропортами вылета (`ORIGINS` в `.env`) и городами назначения В ПОРЯДКЕ
ПРИОРИТЕТА (`DESTINATIONS`, см. ниже), в одну сторону. Модель уведомлений
двухчастная (см. «Модель уведомлений» ниже): (1) алерт, как только
появляется билет дешевле `MAX_PRICE_RUB` — молчит, если ничего нет, не
шлёт лишнего; (2) дайджест дважды в сутки с самой низкой ценой сейчас и
минимальной за прошедший период. Направление не зашито жёстко — маршрут
разворачивался
по ходу использования (Москва/Мин Воды → Нячанг, потом Нячанг → Мин
Воды/Краснодар/Астрахань/Москва, сейчас — Нячанг → Владивосток), вся
логика симметрична и работает в любую сторону.

**Города назначения по приоритету.** `DESTINATIONS` в `.env` — список через
запятую, ПЕРВЫЙ — самый желанный (сейчас только `VVO`: Владивосток; можно
перечислить несколько через запятую, как было раньше с `MRV,KRR,ASF,MOW`).
Бот сравнивает цены во ВСЕ эти города и
берёт самый дешёвый вариант — но если более приоритетный город дороже
самого дешёвого не больше чем на `PRIORITY_MARGIN_RUB` (по умолчанию
10 000 ₽/чел.), показывает его первым, а не просто самый дешёвый: разница
в пределах порога не стоит того, чтобы жертвовать предпочитаемым городом.
Тот же порог и тот же принцип применяется и к выбору "прямой рейс vs рейс
через хаб" — см. ниже. Если приоритетный город не попал в топ-5 карточек по
цене (то есть ощутимо дороже) — его лучший вариант всё равно показывается
отдельным блоком в конце сообщения, чтобы не потерялся. Логика — в
`_apply_priority` в `bot.py`.

**Период поиска.** По умолчанию — скользящее окно `SEARCH_WINDOW_DAYS`
(21 день) от сегодня. Если заданы `SEARCH_START_DATE`/`SEARCH_END_DATE`
(формат `YYYY-MM-DD`) — ищем строго в этом фиксированном периоде вместо
скользящего окна: это для случая, когда даты конкретной поездки уже
известны. Начало окна на месте использования (`_search_window` в `bot.py`)
подрезается по сегодняшнему дню, чтобы не искать в уже прошедшую дату по
мере того, как идёт время.

**Фоновое окно для рыночной статистики.** Помимо основного окна (то, что
реально показывается как варианты для покупки), бот дополнительно забирает
цены ещё на `MARKET_CONTEXT_EXTRA_DAYS` (по умолчанию 10) дней дальше — но
ТОЛЬКО чтобы посчитать медиану рынка (`market_stats`) на более широкой
выборке и понять, дорого сейчас в пределах основного окна или дёшево
относительно более длинного горизонта. Эти дополнительные даты никогда не
показываются как варианты для покупки — см. `run_search` в `bot.py`
(`all_options` для статистики vs отфильтрованный `options` для показа).

**Жёсткий потолок цены.** `MAX_PRICE_RUB` (не задан по умолчанию — без
потолка, сейчас `15000`) — в отличие от `DEFAULT_BUDGET_RUB` (это только
пометка 🔥 в выдаче `/check`), варианты дороже `MAX_PRICE_RUB` за
человека вообще НЕ рассматриваются автоматическим алертом
(`_within_price_cap` в `bot.py`). Если сейчас ничего не укладывается в
потолок — бот молчит, НЕ присылает сообщение "пока дорого" (так по
прямому указанию пользователя; было по-другому раньше — см. историю
изменений в git). Отдельный дайджест дважды в сутки (ниже) потолком не
ограничен — это просто срез рынка, а не алерт.

**Пересадки.** `MAX_TRANSFERS` (не задан по умолчанию — без лимита) —
если задан числом, ни один сегмент билета (прямой или отдельная нога
хаб-маршрута) не покажем, если у него больше пересадок
(`_within_transfer_limit` в `bot.py`). Сейчас лимита нет — по прямому
указанию пользователя, любое число пересадок допустимо.

Помимо прямого варианта, бот для каждой пары (аэропорт вылета × город
назначения) проверяет маршруты через крупные вьетнамские хабы — Хошимин
(SGN), Ханой (HAN), Дананг (DAD) (список — `HUBS` в `config.py`). Хаб-
маршрут состоит из двух ног, и то, какая из них "внутренняя по Вьетнаму"
(ограничена по цене `MAX_DOMESTIC_LEG_RUB`, по умолчанию 8000 ₽), а какая
"международная" (обязана быть **буквально прямым рейсом без пересадок**,
`number_of_changes == 0` в сырых данных `v2/prices/latest`) — зависит от
направления: если вылет уже из Вьетнама (как сейчас) — первая нога
внутренняя, вторая международная; если вылет из России — наоборот. В обоих
случаях именно "длинную" международную ногу требуем прямой — не стоит
стыковать с ещё одной пересадкой уже пересадочный дальний рейс (см.
`_search_via_hub` в `bot.py`). Итоговый список вариантов (прямые + через
хабы, по всем парам вылет×прилёт) сортируется по суммарной цене за
взрослого, дата вылета первой ноги вынесена в начало каждой карточки.

**Заголовок каждого сообщения.** Первая строка любого сообщения от бота —
всегда самый дешёвый прямой билет (один билет, без сборки через хаб — то
же значение "прямой", что и у обычных вариантов, необязательно 0 пересадок
технически) по первому аэропорту вылета и самому приоритетному городу
назначения на ближайшие 3 дня (`_cheapest_direct_headline` в `bot.py`).
Это отдельный, более узкий поиск от основного окна — специально под
наблюдение, что горящие предложения чаще всего появляются за пару-тройку
дней до вылета.

**Запас на пересадку.** Цены берутся из `v2/prices/latest`, а он не отдаёт
время рейсов — но `v1/prices/calendar` для большинства маршрутов (кроме
цены — та ненадёжна для отдельных редких пар) отдаёт настоящее время
вылета (`departure_at`) по датам. Бот использует его вместе с
длительностью рейса (`duration` из `v2/prices/latest`), чтобы оценить
время прилёта первой ноги, и сравнивает с временем вылета второй — если
реальный запас получается ≥ `MIN_HUB_LAYOVER_HOURS` (по умолчанию 6
часов), вариант считается подтверждённым по времени. Если для конкретной
пары дат время не нашлось в календаре (бывает — не для всех дат есть кэш),
используется запасной вариант: минимум `MIN_HUB_LAYOVER_DAYS` суток (по
умолчанию 1) без знания точного времени, и такой вариант помечается в
сообщении значком ⚠️ с пометкой "время рейсов не найдено" — чтобы было
видно, что стыковку нужно свериться самостоятельно перед покупкой. Поиск
второй ноги идёт в окне до `MAX_HUB_LAYOVER_DAYS` (по умолчанию 3) дней
после прилёта первой; если для самой дешёвой даты первой ноги не находится
подходящая пара — бот перебирает следующие по цене даты (до 5 штук).

**Багаж.** Ни один эндпоинт Data API не отдаёт информацию о багаже вообще
(проверено на реальных ответах обоих эндпоинтов) — только время, цену,
авиакомпанию и число пересадок. Поэтому значок 🧳 в сообщении — это НЕ факт
о конкретном тарифе, а ориентир по типу перевозчика (полносервисный обычно
включает багаж в эконом, лоукостер обычно нет), см. таблицу
`AIRLINE_BAGGAGE_INCLUDED` в `config.py`. 🧳✅ — авиакомпания обычно включает
багаж, 🧳❌ — обычно нет (лоукостер), 🧳❓ — авиакомпания не из списка или не
удалось определить. У любого перевозчика бывают разные тарифные классы —
перед покупкой всегда сверяй условия конкретного тарифа на странице
бронирования.

**Надёжность цены (кэш, не живая инвентаризация).** `v2/prices/latest` —
это записи о ценах, которые Aviasales ИЛИ ПАРТНЁРСКИЕ OTA (поле `gate`:
Kupi.com, Aviakassa, City.Travel и т.п.) когда-то уже видели — не проверка
наличия мест прямо сейчас. Практическое следствие: если `gate` — не
"Авиасейлс", цена могла быть найдена на ДРУГОМ сайте с другими агентскими
договорённостями, а ссылка на бронирование всегда ведёт на живой поиск
именно Aviasales — там этой цены (или даже этого рейса) может не
оказаться. Для приоритетных направлений (например, для CXR→VVO)
подавляющее большинство кэша — НЕ с самого Aviasales (проверено на живых
данных 11.08.2026: 0 из 19 записей CXR→VVO были от gate "Авиасейлс" —
все от Kupi.com/Aviakassa/Trip.com/Clickavia). Бот:
1. Фильтрует `actual == False` (сам API помечает часть записей как
   более не актуальные);
2. Отсекает записи старше `MAX_PRICE_AGE_DAYS` (по умолчанию 5 дней) по
   полю `found_at` — снижает, но не убирает риск протухшей цены;
3. Помечает в сообщении значком ⚠️ и именем источника каждую ногу,
   цена которой не с самого Aviasales (`_gate_hint` в `bot.py`);
4. Для таких ног меняет порядок ссылок в сообщении (`_format_leg_line` в
   `bot.py`): ПЕРВОЙ (как "Купить") идёт ссылка на гугл-поиск по тому
   сайту, который реально видел эту цену (`_gate_search_link`) — а ссылка
   на Aviasales идёт ВТОРОЙ, с пометкой "может не найтись". Раньше было
   наоборот (Aviasales первой), из-за чего было легко перейти именно по
   ней и не найти билет. Гугл-поиск, а не прямой deep-link на сам
   агрегатор — осознанный компромисс: для Kupi.com и Aviakassa нет
   публичной документации формата ссылок на конкретный рейс, а угаданные
   по аналогии с Aviasales компактные ссылки на Яндекс.Путешествия и
   Skyscanner упираются в капчу (официальный referral API Skyscanner
   требует `mediaPartnerId`, которого нет).

Формат самой ссылки на aviasales.ru (`build_booking_link` в
`travelpayouts.py`) проверен не только curl'ом (200 OK), но и в реальном
браузере (Playwright, 11.08.2026): форма поиска на странице корректно
предзаполняется нужными городом вылета, городом прилёта, датой и числом
пассажиров — значит сам формат ссылки не сломан. Проблема глубже: у
самого Aviasales для приоритетных направлений почти нет данных вообще —
например, официальный календарь цен (`v1/prices/calendar`) для CXR→ASF
в августе 2026 не содержит НИ ОДНОЙ даты (единственная дата за весь
охваченный период — в сентябре). Это подтверждает, что билет может не
найтись по ссылке не из-за бага в боте, а потому что у Aviasales
физически нет этих данных прямо сейчас — отсюда и смена порядка ссылок
в пункте 4 выше. Полностью автоматически проверить, что видит живой
человек при переходе по ссылке, не вышло: сам Aviasales блокирует
автоматизированные заходы капчей (эксперимент `smartcaptcha` виден в его
собственных сетевых запросах) — обычного пользователя это не касается.

Также в каждой ноге бота показано число пересадок (`_transfers_hint`,
поле `number_of_changes` из сырых данных API) — прямо в сообщении, без
необходимости переходить по ссылке, чтобы это узнать.

Тем не менее ограничение "кэш, не живая инвентаризация" — принципиальное
свойство бесплатного Data API, не временный баг: часть показанных цен
может не подтвердиться при попытке купить. Единственный полностью
надёжный способ узнать точную цену — `v1/flight_search` (закрытый
live-поиск, см. ниже, почему не используем).

## Как это устроено (и почему именно так)

Есть два вида API у Travelpayouts (агрегатор Aviasales):

1. **Live-поиск с реальным числом пассажиров** (`flight_search`) — даёт точную
   цену здесь и сейчас, но доступ выдают только партнёрам с 50 000+ MAU на
   сайте, и правила прямо запрещают использовать его для автоматического
   мониторинга/сбора цен в фоне. Для нашей задачи он не подходит и не нужен.
2. **Data API** (`v2/prices/latest`) — это как раз официально предназначено
   "для сайта или блога", открыто любому, у кого есть токен Travelpayouts.
   Отдаёт кэш минимальных цен, которые Aviasales уже видел по маршруту,
   **из расчёта на одного взрослого**.

Бот использует второй вариант, конкретно `v2/prices/latest?one_way=true`.
Изначально была попытка взять `v1/prices/calendar` (там красивая выдача по
дням на весь месяц), но эмпирическая проверка на реальном токене показала:
для маршрута MOW→NHA этот эндпоинт **игнорирует флаг one_way** и всегда
отдаёт кэш цен туда-обратно (поле `return_at` заполнено настоящей датой
обратного рейса, даже когда `return_date` в запросе не передан). А
`v2/prices/latest?one_way=true` отдаёт честные one-way записи (`return_date`
пустой) — это проверено на живых данных, поэтому используется он.

Раз в N минут бот тянет цены на ближайшие 21 день (или на скользящее
`SEARCH_WINDOW_DAYS`) и показывает цену за одного взрослого пассажира
(`settings.adults`, сейчас `1`) — при желании искать на нескольких
пассажиров меняется в `Settings.adults`/`children`/`infants` в
`config.py`, дальше всё (оценка суммарной цены, текст сообщений, кодировка
пассажиров в ссылке) считается от этого значения автоматически.

**Важно:** цена в алерте — это ориентир, а не гарантия. Перед покупкой всегда
проверяй финальную стоимость по ссылке из сообщения.

## Модель уведомлений

Плановая (фоновая) проверка — `_scheduled_check` в `bot.py`, вызывается
на каждом прогоне workflow (сейчас — раз в `CHECK_INTERVAL_MINUTES`,
реально ~10 мин, см. ниже про ненадёжность `schedule`). У неё ДВА
независимых поведения — это прямое указание пользователя, замена более
ранней версии, где бот писал безусловно на каждой проверке (история — в
git):

**1. Алерт по потолку цены** (`_check_cheap_alert`). Как только среди
найденных вариантов появляется билет в пределах `MAX_PRICE_RUB` (любое
число пересадок — `MAX_TRANSFERS` не задан) — бот сразу присылает его
одним сообщением (`🔥 Нашёл билет...`). "Появляется" — не то же самое,
что "есть": если тот же самый билет (та же цена) находится и на
следующей проверке, повторно не шлём — только когда цена меняется или
билет пропадал, а потом нашёлся снова (состояние `cheap_alert_active`/
`cheap_alert_price` в `data/state.json`). Если сейчас ничего нет —
бот молчит, вообще не пишет ни строчки.

**2. Дайджест дважды в сутки** (`_update_period_min` + `_maybe_send_digest`,
время — `_DIGEST_HOURS_UTC` в `bot.py`, сейчас `(3, 15)` UTC — на
усмотрение бота, раз в 12 часов). Не связан с потолком цены — это просто
срез рынка: самая низкая цена, которая есть ПРЯМО СЕЙЧАС, и самая низкая
цена, которая БЫЛА за период с прошлого дайджеста (накапливается на
каждой плановой проверке в `period_min_price`/`period_min_text`, сбрасывается
после отправки дайджеста). У обеих — число пересадок и время в пути
(`_transfers_hint`/`_format_duration`, из полей `number_of_changes` и
`duration` в сырых данных `v2/prices/latest`). `slot_key` (дата+час) в
состоянии чата защищает от повторной отправки, если прогон в этот же час
случится больше одного раза — `schedule` в GitHub Actions не гарантирует
точность (см. ниже).

**Что считается выгодной сделкой в `/check`** (`_deal_tags` в `bot.py`) —
`/check` (ручной запрос) работает ПО-ДРУГОМУ: показывает полную картину
(топ-5 вариантов, медиана рынка) вне зависимости от потолка, отмечает
прямо в тексте, не блокируя отправку:
- цена ≤ порога `DEFAULT_BUDGET_RUB` за ОДНОГО человека (по умолчанию
  30 000 ₽, меняется через `/setbudget`) — отметка 🔥;
- цена ≤ 85% (`MARKET_BEATING_RATIO`) от медианы по всем вариантам,
  найденным в текущей проверке (`market_stats`) — отметка 🎯.

Это отдельная, независимая от алерта/дайджеста логика — `/setbudget` на
плановые сообщения не влияет.

**Баг с планировщиком (пофиксен).** Первая версия передавала в APScheduler
`next_run_time=datetime.now()` (наивное время, без часового пояса) при
`AsyncIOScheduler(timezone="Europe/Moscow")`. Если сервер физически не в
московском часовом поясе, наивное время интерпретируется библиотекой как
московское — и "немедленный" первый запуск на деле откладывается на разницу
поясов (в нашем случае бот не присылал первое сообщение ~4 часа после
старта, пока это не нашли). Исправлено: первая проверка теперь просто
вызывается явно (`await scheduled_job()` в `main()`) перед стартом
интервального расписания, без завязки на часовые пояса.

## Время вылета

Рядом с датой каждого рейса бот показывает локальное время вылета (как оно
и указывается на самом билете), если оно нашлось в календаре Aviasales —
`_format_leg_datetime` в `bot.py`, использует то же `departure_at`, что и
расчёт запаса на пересадку. Если для конкретной даты время не нашлось —
показывается только дата, без домысливания.

## Ссылки на билеты

Ссылки ведут на `https://www.aviasales.ru/search/<код>` — компактный формат
вида `MOW2407CXR12` (аэропорт вылета + дата ДДММ + аэропорт назначения +
цифры пассажиров: взрослые-дети-младенцы слитно, без замыкающих нулей).
Это подтверждённо рабочий формат: запросы к нему отдают чистый HTTP 200
без редиректов, это же официальный формат шаринг-ссылок с сайта (у него
свой `og:description` вида "MOW (24.07) - CXR, 1 пассажир, эконом").

**Важно:** ранее бот использовал query-параметры (`origin_iata=...` на
`search.aviasales.com/flights`) — этот формат оказался сломан: реальный
HTTP-запрос к нему получает 302-редирект на голую главную страницу
aviasales.ru без единого параметра (проверено curl'ом, в том числе с
подделкой User-Agent под браузер). Сейчас так не делаем.

Кодировка маршрута, даты и числа пассажиров (`{adults}{children}{infants}`,
без замыкающих нулей) подтверждена не только curl'ом (200 OK), но и в
реальном браузере (Playwright, 11.08.2026): форма поиска на странице
корректно предзаполняется нужными городами, датой и числом пассажиров —
проверено и на "1" (1 взрослый), и на "3" (3 взрослых).

## Шаг 1. Создать Telegram-бота

1. В Telegram напиши [@BotFather](https://t.me/BotFather) → `/newbot`.
2. Придумай имя и username (должен заканчиваться на `bot`, например
   `msk_nhatrang_prices_bot`).
3. BotFather пришлёт токен вида `123456789:AAExxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`
   — это `TELEGRAM_BOT_TOKEN`.

## Шаг 2. Получить доступ к Travelpayouts Data API

1. Зарегистрируйся на [travelpayouts.com](https://www.travelpayouts.com/) как
   партнёр (это бесплатно, регистрация — как для affiliate-программы, но нам
   нужен только доступ к API, ничего продавать не обязательно).
2. В личном кабинете: **Tools → API** (или "Мои сайты/приложения" → добавить
   заявку с любым описанием, например "личный бот для мониторинга цен") —
   получишь **API-токен** (`TRAVELPAYOUTS_TOKEN`) и увидишь свой **marker**
   (партнёрский ID, `TRAVELPAYOUTS_MARKER`, число вроде `123456`).
3. `TRAVELPAYOUTS_MARKER` не обязателен для получения цен, но без него ссылки
   на покупку в сообщениях бота не будут засчитываться тебе как переходы —
   лучше указать.

## Шаг 3. Настроить и запустить

```bash
cd ~/projects/msk-nhatrang-flight-bot
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# открой .env и вставь TELEGRAM_BOT_TOKEN, TRAVELPAYOUTS_TOKEN, TRAVELPAYOUTS_MARKER
python bot.py
```

В Telegram найди своего бота по username и отправь `/start` — он подпишет
этот чат на уведомления и покажет текущие настройки.

## Команды бота

- `/start` — подписаться на уведомления, показать настройки
- `/check` — проверить цены прямо сейчас (не дожидаясь расписания)
- `/setbudget 35000` — изменить порог алерта (в рублях, на всех пассажиров)
- `/status` — показать маршрут, окно поиска, порог, периодичность
- `/stop` — отписаться от уведомлений

## Настройки (файл `.env`, все необязательны кроме токенов)

| Переменная | По умолчанию | Что значит |
|---|---|---|
| `ORIGINS` | `MOW,MRV` | IATA-коды аэропортов вылета через запятую |
| `DESTINATIONS` | `CXR` | IATA-коды городов назначения через запятую, В ПОРЯДКЕ ПРИОРИТЕТА (первый — самый желанный) |
| `SEARCH_START_DATE` / `SEARCH_END_DATE` | не заданы | Фиксированный период конкретной поездки (`YYYY-MM-DD`); если оба заданы — вместо скользящего окна |
| `SEARCH_WINDOW_DAYS` | `21` | Скользящее окно от сегодня — используется, только если `SEARCH_START_DATE`/`SEARCH_END_DATE` не заданы |
| `MARKET_CONTEXT_EXTRA_DAYS` | `10` | На сколько дней дальше основного окна фоново смотрим цены ТОЛЬКО для медианы рынка — эти даты не показываются как варианты |
| `CHECK_INTERVAL_MINUTES` | `20` | Только для текста в `/status`/`/start` — на реальное расписание в GitHub Actions влияет `cron` в workflow, не эта переменная |
| `DEFAULT_BUDGET_RUB` | `30000` | Порог отметки 🔥 за ОДНОГО человека, пока не задан `/setbudget` — просто пометка, варианты дороже всё равно показываются |
| `MAX_PRICE_RUB` | не задан (без потолка) | ЖЁСТКИЙ потолок цены за ОДНОГО человека — варианты дороже вообще не показываются (не пометка, а фильтр) |
| `MAX_DOMESTIC_LEG_RUB` | `8000` | Внутреннюю (по Вьетнаму) ногу хаб-маршрута учитываем, только если дешевле этого |
| `MAX_TRANSFERS` | не задан (без лимита) | Если задано числом — не предлагаем билет (ни прямой, ни отдельный сегмент хаб-маршрута), если у него больше этого числа пересадок |
| `MAX_PRICE_AGE_DAYS` | `5` | Отсекаем записи из кэша Data API старше этого числа дней по полю `found_at` — снижает риск протухшей цены |
| `PRIORITY_MARGIN_RUB` | `10000` | Порог "почти одинаковая цена — предпочитаем по приоритету, а не по минимальной цене": и для прямой/хаб, и для выбора между городами `DESTINATIONS` |
| `ENABLE_HUB_SEARCH` | `true` | Выключи (`false`), если маршрут не связан с Вьетнамом и хабы искать не нужно |
| `MIN_HUB_LAYOVER_HOURS` | `6` | Минимальный подтверждённый по времени запас на пересадку через хаб |
| `MIN_HUB_LAYOVER_DAYS` / `MAX_HUB_LAYOVER_DAYS` | `1` / `3` | Запасной вариант по датам, если точное время рейсов не нашлось в календаре |

Про частоту проверки: у Data API нет жёсткого официального лимита запросов
(в отличие от live-поиска, там 200/час), но сами цены в кэше Aviasales
обновляются не мгновенно — проверка чаще 5-10 минут почти наверняка не даст
более свежих данных, только зря грузит API. Реальное расписание задаётся
`cron` в `.github/workflows/check-flights.yml` (сейчас `*/10`), а не
`CHECK_INTERVAL_MINUTES` — эта переменная используется только для текста в
сообщениях бота, держи её в согласии с `cron` вручную.

## Постоянный запуск (чтобы бот работал 24/7)

### Сейчас используется: GitHub Actions по расписанию (бесплатно, без сервера)

Все нормальные бесплатные VPS/облака (Google Cloud, Oracle Cloud, Hetzner —
пробовали именно в таком порядке) в 2026 году требуют подтверждение номером
телефона при регистрации — это стало отраслевым стандартом анти-фрод защиты.
Раз готового сервера без телефона не нашлось, решили не привязываться к
серверу вообще: `.github/workflows/check-flights.yml` запускает
`run_once.py` каждые `*/10 * * * *` (см. `CHECK_INTERVAL_MINUTES`) прямо на
раннерах GitHub, без обслуживания и без привязки к тому, включён ли чей-то
компьютер.

**Почему репозиторий публичный.** У приватных репо бесплатный лимит GitHub
Actions — 2000 минут/мес, и из-за того, как cron считает интервалы (число
запусков в час одинаковое для любого N от 20 до 29 минут — модульная
арифметика, не "честные" 20 или 25), безопасно уместиться можно было только
на 30-минутный интервал (~1490 мин/мес). Чтобы проверять чаще (цель — почаще
видеть цены, не только редкие алерты), репозиторий сделали публичным — у
публичных репо минуты GitHub Actions бесплатны без ограничения. Секреты
(токены) всё равно остаются скрытыми — они лежат в encrypted Secrets, а не
в коде, и не отображаются даже в публичном репозитории.

**Как это устроено.** `run_once.py` — это НЕ то же самое, что постоянный
`bot.py` из предыдущих разделов: вместо бесконечного
`Dispatcher.start_polling()` (что требует висящего процесса) он:
1. Забирает накопившиеся апдейты Telegram через `bot.get_updates(offset=...)`
   — короткий разовый опрос, а не long polling — и прогоняет их через тот же
   `dp` (`Dispatcher.feed_update`), так что все обработчики команд
   (`/start`, `/check`, `/setbudget`, `/status`, `/stop`) из `bot.py` работают
   без изменений;
2. Прогоняет `scheduled_job()` — ту же плановую проверку цен, что и раньше;
3. Обновляет `data/last_run.txt` (просто таймстамп) — подстраховка на
   случай, если `run_search` когда-нибудь снова станет условным (не на
   каждом прогоне): GitHub автоматически отключает `schedule`-триггер после
   60 дней без активности в репозитории, а этот файл гарантирует, что
   активность есть всегда, даже если `data/state.json` не поменяется;
4. Процесс завершается, шаг workflow "Commit updated state" коммитит
   `data/` обратно в репозиторий — это и есть вся персистентность между
   запусками (офсет апдейтов Telegram, история алертов на чат).

**Важный компромисс:** раз процесс не висит постоянно, `/check` и
`/setbudget` отвечают не мгновенно, а на ближайшем плановом прогоне (то
есть с задержкой до `CHECK_INTERVAL_MINUTES`). Проактивные алерты о
выгодных билетах на это не влияют — работают как раньше.

**Ненадёжность встроенного `schedule`.** GitHub НЕ гарантирует частоту
cron-триггера — на истории прогонов 02-06.08.2026 при `*/10 * * * *`
реальные интервалы между срабатываниями были от ~1 часа до 12 часов, а не
обещанные 10 минут. Для цели "хотя бы пара сообщений в день" этого с
запасом хватает (даже в худшие дни было больше двух срабатываний), но
если понадобится по-настоящему частая и предсказуемая доставка — есть
запасной план ниже.

Важно: это НЕ авторизация или разрыв соединения — `gh auth status` и
история прогонов (`gh run list`) при проверке 11.08.2026 показывают 100%
успешных завершений без единой ошибки. То, что ощущается как "бот
периодически отваливается", на самом деле неравномерные интервалы между
срабатываниями `schedule` — сам GitHub Actions и токен работают исправно
на каждом прогоне.

**Внешний триггер (не настроен, план на будущее).** Вместо встроенного
`schedule` можно дёргать `workflow_dispatch` через GitHub API из внешнего
бесплатного cron-сервиса (например, cron-job.org) — исполнение всё равно
остаётся на GitHub Actions, просто триггер надёжнее. Понадобится:
1. Fine-grained Personal Access Token на GitHub (Settings → Developer
   settings → Personal access tokens → Fine-grained tokens), доступ только
   к этому репозиторию, права Actions → Read and write;
2. Cronjob на внешнем сервисе: `POST` на
   `https://api.github.com/repos/capastreet-wq/msk-nhatrang-flight-bot/actions/workflows/check-flights.yml/dispatches`,
   заголовки `Authorization: Bearer <токен>`, `Accept: application/vnd.github+json`,
   тело `{"ref":"main"}`.

Не настроено — это только план на случай, если встроенного `schedule`
когда-нибудь снова станет мало.

**Секреты** (`TELEGRAM_BOT_TOKEN`, `TRAVELPAYOUTS_TOKEN`,
`TRAVELPAYOUTS_MARKER`) заданы через `gh secret set` — Settings → Secrets
and variables → Actions в репозитории на GitHub. Права на запись для
`GITHUB_TOKEN` включены отдельно (Settings → Actions → General → Workflow
permissions → Read and write), без этого шаг коммита в конце свалится с
403.

Управление:
```bash
gh workflow run check-flights.yml       # прогнать вручную, не дожидаясь расписания
gh run list --workflow=check-flights.yml --limit 5   # история прогонов
gh run view <id> --log                  # логи конкретного прогона
```

### Альтернатива: локально на своей машине — `launchd` (macOS) / `systemd` (Linux)

Раньше бот был поднят через `launchd` прямо на Mac пользователя — рабочий
вариант, но зависит от того, включён ли и залогинен ли конкретно этот
компьютер (сейчас отключён, `launchctl bootout`, чтобы не спорить с GitHub
Actions за один и тот же токен бота — Telegram не разрешает двум
процессам одновременно опрашивать `getUpdates`). Если решишь вернуться к
этому варианту:

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.sofa.nhatrang-flight-bot.plist
```

(конфиг `~/Library/LaunchAgents/com.sofa.nhatrang-flight-bot.plist` никуда
не делся, просто выгружен) — но тогда GitHub Actions workflow нужно
отключить (`gh workflow disable check-flights.yml`), иначе будет тот же
конфликт двух консьюмеров `getUpdates`.

### На Linux-сервере/VPS — `systemd`

```ini
# /etc/systemd/system/nhatrang-flight-bot.service
[Unit]
Description=Nha Trang flight price bot
After=network.target

[Service]
WorkingDirectory=/path/to/msk-nhatrang-flight-bot
ExecStart=/path/to/msk-nhatrang-flight-bot/.venv/bin/python bot.py
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now nhatrang-flight-bot
```

Либо через Docker:

```bash
docker build -t nhatrang-flight-bot .
docker run -d --restart unless-stopped --env-file .env -v $(pwd)/data:/app/data nhatrang-flight-bot
```

## Ограничения, о которых стоит знать

- Цена в алерте — прямо из кэша Data API за 1 взрослого (сейчас
  `settings.adults=1`, дополнительно ни на что не умножается). Реальная
  цена при переходе по ссылке может отличаться (динамическое
  ценообразование, разные тарифные корзины) — сверяйся перед покупкой.
- Прямых рейсов Москва — Нячанг может не быть в конкретные даты (обычно это
  чартеры сезонно или рейсы с пересадкой) — бот покажет любые варианты
  (включая пересадки), которые есть в кэше Aviasales.
- Если по направлению совсем нет данных (редкий узкий маршрут вне сезона),
  бот честно скажет "данных нет" и даст ссылку для ручной проверки.
